# 游戏运行时与重构架构

## 当前技术栈

- React + TypeScript + Vite：浏览器试玩与最终 Renderer；
- 纯 TypeScript：领域规则、数值结算、事件选择和世界模拟；
- Electron Main + preload：最终桌面壳与窄系统接口；
- SQLite：最终本地存档；
- Vitest + Testing Library：规则、集成和界面测试。

用户已明确决定不采用 Godot。项目继续使用 React + TypeScript + Vite 完成浏览器审查面，最终使用 Electron + SQLite 形成桌面版本；不建立Godot分支、不做React/Godot双运行时，也不重写现有领域规则。只有玩家以后明确把产品改成以可移动场景、实时战斗或重度物理/动画为核心时，才重新评估游戏引擎。

## 1. 架构目标

这套架构只服务三个玩家目标：每次选择都能得到可解释反馈，完整周目能够可靠保存，22 条途径可以持续扩充而不污染彼此。它不是审批流程，也不以图、哈希或状态回执代替真实玩法。

重构保留当前已经验证有价值的部分：类型化意图、确定性随机、日历、普通判定、单张阻塞事件、公开状态边界和 SQLite 单事务提交。需要拆开的主要问题是：`PublicGameState` 同时承担内部存档和界面投影、行动结算文件过大、浏览器与 SQLite 各自编排规则、正式内容与 fixture 边界不足，以及尚无途径运行时。

## 2. 目标运行分层

```text
React 周仪表盘
  ⇅ 公开投影 / 类型化意图
公共边界（schema、版本、可见知识）
  ⇅
应用编排器（一次意图、一次提交）
  ├─ 核心领域状态与不变量
  ├─ 普通判定 / 多回合转盘战斗 / 确定性随机
  ├─ 途径运行时
  ├─ 事件、对话、世界脉冲与分层人物模拟
  └─ 版本化内容注册表
  ⇅ Repository Port
  ├─ 浏览器内存适配器（开发试玩）
  └─ Electron Main + SQLite（正式存档）
```

浏览器适配器和 Electron 适配器必须调用同一套领域规则。浏览器刷新重置是开发限制，不得描述为正式存档。

RAG 表现器位于公开事实之后，只能把已经确定的事实包变成可见文案，并始终保留固定文本回退。它没有返回领域层的依赖箭头。

## 3. 模块责任与目标目录

- `src/renderer/**`：屏幕、交互、焦点、视觉反馈；不直接访问 Node、文件系统或 SQLite。
- `src/shared/**`：公开意图、公开投影、回执、错误与合同版本；不暴露隐藏世界状态、未匹配事件选项、私有匹配条件或隐藏选项数量。
- `src/application/**`：加载状态、选择内容版本、调用领域规则、提交回执和生成公开投影。该目录是重构目标，当前编排逻辑仍分散在 bridge/store 中。
- `src/domain/**`：内部 `GameState`、不变量和纯状态变换；`domain/pathways/**` 承担途径状态、晋升与能力生命周期。
- `src/resolution/**`：普通判定、随机流、行动预算和战斗结算。
- `src/simulation/**`：周脉冲、事件调度、原著关键人物、轻量具名角色与组织/地区聚合状态；浏览器适配器在重构后不再拥有规则编排。
- `src/content/**`：版本化注册表、schema 和数据包；按 `pathways/`、`events/`、`characters/`、`world/` 组织。
- `src/persistence/**`：Repository Port、存档编码、迁移、SQLite 事务、备份与恢复。
- `src/main/**`：Electron 窗口、安全、IPC 校验与存档编排。

这些目录是责任边界，不是审批边界。为了清晰实现可以在重构中调整文件，只要依赖方向和运行时安全保持明确。

## 4. 一次意图的执行链

```text
1. Renderer 发送 IntentEnvelope(intentId, expectedRevision, payload)
2. 公共边界校验 schema、合同版本与发送方
3. 应用编排器从 Repository 加载内部 GameState
4. 检查 lifecycle、revision、当前阻塞事件与玩家是否有权执行
5. 按存档中的 contentVersion 加载内容注册表
6. 为本次动作建立可记录的确定性随机流
7. 领域层执行行动 / 事件 / 晋升 / 战斗命令
8. 事件与世界模拟消费领域事件，生成即时或延迟后果
9. 校验新状态，在一个事务中保存状态、随机记录和 CommitReceipt
10. Projector 只输出玩家当前可见的 PublicGameState
```

第 7—8 步产生的是纯数据结果，不直接更新 React、写 SQLite 或调用模型。任一步失败都不允许部分写入。

## 5. 内部状态与公开投影

目标内部状态至少按以下切片组织：

- `run`：周目、生命周期、日期、revision、规则/内容/存档版本；
- `character`：身份、四项能力、健康/精神/灵性/污染、资金与职业；
- `pathway`：当前途径/序列、明确扮演进度、定性消化阶段、逐能力掌握和晋升准备；
- `inventory`：物品、材料、封印物实例与来源；
- `knowledge`：已知事实、传闻、线索与来源；
- `events`：周脉冲待执行标记、当前阻塞卡、待办选择、计划事件、事件链、冷却与历史；
- `combat`：当前遭遇、回合、战术姿态、次数/能力/目标/胜负/败者后果盘、预授权消耗品、伤势层级和累计死亡风险；
- `world`：原著基线与当前分支、当前城市/已解锁目的地、关键人物状态、轻量具名角色、组织综合关系阶段/当前议程、地区聚合状态、延迟和潜伏后果；
- `random`：动作级 seed、流位置与必要回放记录；
- `chronicle`：已提交的玩家行为、公开结果和终局封存摘要。

`PublicGameState` 由 Projector 生成，不再作为全部内部状态的同义词。隐藏触发条件、NPC 目标、未揭露内容、抽取权重和私有 RAG 证据不能进入 Renderer。

## 6. 状态与随机

- 所有正式状态必须是可序列化纯数据，不保存函数、DOM 节点、数据库句柄或模型对象。
- 公开投影与隐藏世界状态分开；Renderer不接收暂不可见事实、未匹配的途径/序列特殊选项、选项数量、私有RAG上下文或内部堆栈。
- 随机源由动作级 seed 驱动并记录消耗顺序；相同输入、状态和 seed 必须可重放。
- 每次玩家意图返回单一结果：接受后的新版本与回执，或没有部分写入的明确失败。

所有领域规则接收显式 `RandomStream`，生产代码禁止直接调用 `Math.random()`。事件抽取、战斗盘、晋升风险与世界脉冲可以使用不同命名子流，避免新增一个随机调用就改变所有后续结果。

## 7. 存档与双适配器

正式桌面版提供多个周目槽位。每个槽位只有一个随已提交状态向前滚动的自动存档和一个最近可恢复备份；不提供战斗前、事件前或晋升前的手动回滚存档。死亡槽位转为只读封存，跨周目只解锁档案/结局/图鉴，不把机械加成写入新角色。

存档结构必须包含版本号，并为每次 schema 变化提供迁移。桌面写入遵循：

1. 校验待保存状态；
2. 在同一卷写临时文件或事务；
3. 原子提交；
4. 保留最近一次可恢复备份；
5. 启动时校验、迁移或回退，不静默丢档。

自动保存发生在领域提交边界：行动结果、事件选择、市场交易、晋升结果以及每个完整战斗回合/败者后果结算后。转盘动画和未提交的界面选择不生成存档点；崩溃恢复只回到最近一次已提交 revision，不能借恢复重新抽取结果。

浏览器内存适配器和 SQLite 适配器实现同一个 Repository Port；二者调用同一个应用编排器和领域规则。浏览器刷新重置是开发限制，界面必须明确显示，不能描述成正式存档。

SQLite 至少分离周目快照、意图回执与 schema 迁移。是否进一步拆分事件历史或表现文本，由真实查询与恢复需求决定，不预先复制 gmzz 或旧原型的 schema。Windows 桌面环境优先依靠 SQLite 事务；导出/导入文件使用同目录临时文件、原子替换和 `.bak`。

## 8. 内容注册表与途径运行时

- 内容定义使用稳定 ID、schema 版本、来源状态和纯数据条件。
- 数据文件禁止任意函数和原始 HTML。
- 通用效果通过声明式操作表达；真正特殊的能力进入显式处理器注册表并配测试。
- 事件、能力和对话文本使用稳定文本 ID，便于回放、存档迁移和本地化。

内容注册表启动时完成：schema 校验、ID 唯一性、交叉引用、序列 9—0 顺序、效果类型、处理器存在性、文本回退和来源字段检查。保存的周目绑定 `contentVersion`；内容升级通过显式迁移或继续加载兼容包，不能静默让旧档采用新规则。

途径运行时不拥有自己的时间、事件队列或存档。它接收领域命令与当前内容包，返回能力效果、资源变化和领域事件，再由共用编排器继续结算。完整玩家路径与数据结构见 [途径玩法与内容架构](PATHWAY_GAMEPLAY_ARCHITECTURE.md)。

## 9. 事件、对话与世界模拟

- 事件和对话使用纯数据节点、稳定选择 ID、条件、成本与效果，不在内容文件内嵌函数；
- 一次只允许一个页面级阻塞事件；已经生成的待办选择必须逐张全部解决，才能提交下一个主要行动或结束本周。内部计划事件和不可操作纪事不阻塞玩家，也不与待办共用状态；
- 工作、学习、调查、休养都能成为事件来源和扮演证据入口；事件解析后才判定是否推进扮演，按钮本身不加进度；
- 原著关键人物使用手工状态机表达长期阶段，用 Utility 评分在已审核合法行动中选择当前意图；人物拥有稳定 ID、存活/可用状态、位置、归属、关系阶段、近期原因和专属事件引用；
- 其他具名角色使用轻量槽位，只保存当前事件需要的身份、关系、可用性和近期原因；姓名从内容或确定性名字池取得；
- 原著主要组织使用轻量聚合状态，每个组织只保存一条综合关系阶段、一个当前议程、地区活动和事件资格；玩家默认无正式组织，只有已提交的加入事件选择才能建立归属，同一时间最多一个主要正式组织；
- 首版不做全城寻路或全人物逐帧模拟。每次已提交行动和周脉冲只更新受影响的角色、组织、地区与延迟后果；
- 世界以原著同期事实为初始基线，但不是不可变脚本。人物死亡、归属变化或关键条件破坏后，调度器必须重验所有 `actorRefs/continuityDeps`，取消、替换或进入已审核分支；
- 世界脉冲只消费已提交结果，输出即时、延迟或潜伏后果以及玩家可见消息。

当前城市及与玩家直接相关的人物/组织执行高精度更新；远方只推进原著时间线、组织态势与公开消息。轻量迁居不引入地图引擎：已解锁目的地通过类型化情境意图发起，消耗一次主要行动和明确旅费，再由迁居事件卡提交城市切换。途径与组织归属是独立状态；内容校验必须拒绝“只有加入某组织才能继续该途径”的唯一晋升依赖。

最后一个主要行动耗尽行动次数时，只先写入“周脉冲待执行”。如果该行动生成阻塞事件或本批已有待办选择，必须逐张解决并提交；本批清空后系统立即推进日期、执行完整周脉冲和重新校验连续性，不再等待单独的结束周意图。不能因为卡片打开而跳过本周世界更新。事件弧、容器迁移和连续性失效规则见[事件卡系统](EVENT_CARD_SYSTEM.md)。

事件内容分为共享生活层、精确序列模板包与逐途径内容变体。共享117个定义只是普通人/低序列第一批底座，不是22条途径剧情已经完成的证明或内容上限。应用层先按普通人或当前`exactSequence`选择模板包，再按`pathwayId`装载独立`PathwayEventVariant`，最后在该变体内处理能力、掌握度、资源和知识隐藏条件；不能先选一张跨序列通用卡再挂220个分支。普通人阶段候选池以日常内容为主，阻塞卡目标密度为每周1—2张；成为非凡者后，以非凡相关事件约占70%、每周2—3张阻塞卡为体验目标。该比例和密度由内容标签、候选权重和试玩统计共同校准，不在单周强行配额。周脉冲产生的所有玩家当前可知更新都进入公开列表，不以固定条数截断；隐藏事实与未匹配选项仍完全省略。

## 10. UI 运行结构

界面按屏幕栈而不是散落弹窗组织：

```text
基础层：角色创建 或 周仪表盘
阻塞层：事件 / 晋升 / 必须回应的后果
战斗层：全屏多回合转盘战斗舞台
终局层：死亡封存与周目摘要
系统层：设置、存档、帮助
```

阻塞层出现时，背景必须 `inert`、焦点进入弹层、Escape 不得跳过必须选择的后果；关闭后焦点回到触发位置。状态更新由提交后的公开投影驱动，不由组件自行猜测金钱、能力或事件结果。

## 11. AI/RAG 边界

规则引擎先决定事实、参与者、人物生死、选项与结果，RAG/模型最后只生成表现文本。模型输出必须经过长度、可见知识、来源和安全校验；任何失败都回退到固定文本。

gmzz 只用于参考这一条 RAG 管线的候选检索、来源追踪与泄漏防线。其他架构均根据本游戏自身需求实现，不从 gmzz 复制。

运行时表现请求只包含允许公开的事实 ID、语气约束、长度和固定回退文本 ID。通过校验的生成文案必须作为与回执/事件实例绑定的表现记录保存，保证同一存档重读与复盘一致；它不能成为任何条件、数值或后续规则的输入。事件规则模板和大批叙事变体优先在作者/构建期借助 RAG 与小模型生成、校验、审核并缓存；运行时模型只做既定公开事实的即时措辞差异。

## 12. 重构顺序

1. 定义内部 `GameState`、公开 Projector 与 Repository Port，保持现有浏览器纵切可玩；
2. 把 bridge/store 中重复的意图编排收敛到 `src/application/**`；
3. 拆分当前行动结算为命令处理器、效果应用器、事件调度与周脉冲；
4. 建立版本化内容注册表和声明式效果；
5. 用一个调查连环案、关键人物、轻量角色和组织反应实现事件卡＋世界模拟纵切；
6. 按 [途径玩法与内容架构](PATHWAY_GAMEPLAY_ARCHITECTURE.md)实现占卜家序列 9 纵切；
7. 接回 Electron/SQLite，完成迁移、重启恢复与桌面验证；
8. 用观众和猎人检验扩展点，再推进其余途径。

每一步都保持可运行纵切，避免先搬空旧代码再等待大重写完成。

## 13. 架构维护

旧 Archify 图和哈希回执已归档。当前轻量图见 [游戏运行时架构](architecture/game-runtime-architecture.html)，它用于理解和讨论，不构成开发门禁。判断架构是否健康主要看：依赖是否清晰、规则能否独立测试、状态是否可重放、存档是否可恢复，以及真实玩法是否顺畅。
