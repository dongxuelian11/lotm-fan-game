本文件保留底层模块与旧 S0—S5 技术切片，供实现时查阅；跨任务轮次、前后端写集、接线和用户审查以 [主开发计划](MASTER_DEVELOPMENT_PLAN.md) 为准。R1 已完成前后端接线与本机自动门禁，当前为 `R1_INTEGRATED_AWAITING_PLAYER_ACCEPTANCE`；R2 尚未冻结或下发。

## 施工顺序

### 0. 设计封板

战斗底层批次 `D-GRILLBATCH6..8`、事件卡结构 `D-EVENT1..18` 与 UI `D-UI1..3` 已收口。一次性物品、先手数值和后果公开层级已延期，不阻塞最小纵切。不要批量写入具体途径能力；未决项必须保持原状态。

底层工程已经具备分阶段开工条件：`D-IMPLEMENTORDER1` 明确不必等待22条途径全部能力完成。R1 已用普通人 fixture 验证桌面壳、窄 bridge、SQLite 权威提交与重启恢复；R2 只有在用户通过 R1 界面审查且主任务冻结新合同后才能开始。事件工具可按 `D-EVENT10=A` 预留构建期变体与固定文本兜底接口，但生产模型链后置；魔药/扮演/晋升和完整能力内容继续等对应轮次 Grill。

### 1. 底层引擎

建议先建立与题材无关的公共模块：

- 领域状态：角色、资源、技能、能力、状态、事件、世界周次；
- 经济状态：现金（便士）、生活档位、债务、产业资产、黑市挂牌和季度拍卖；
- 普通判定：可行性、d100四档、双轴后果和 `onZero`；
- 战斗：次数盘、能力盘、回合快照、基础战势、胜负盘、生存盘；
- 能力结果：条件、目标、资源、状态、事件后果和日志；不建立独立公共效果事务；
- 随机：行动级种子、固定取数顺序、重放记录；
- 内容：能力/事件卡 schema、版本、来源、校验、数据装载和受控扩展处理器；
- 持久化：权威存档、事务、版本、重启恢复和终局只读封存。

这一步可以使用测试占位能力和假事件验证，不需要等待22条途径的全部数值。

### 2. 内容工具与最小纵切

底层稳定后，先选择已确认的首版范围逐步录入：普通人创建、三条途径的序列9—7、基础调查、学习/工作/休养、经济/产业、黑市/季度拍卖、事件卡和少量战斗。每项能力、事件卡、商品和事件链都用数据记录，只有确实无法表达的能力才登记扩展处理器；事件卡按 [事件卡系统与内容生产](EVENT_CARD_SYSTEM.md) 的 fixture→内容包顺序加入。

### 3. 分批扩展与校准

按途径/序列完成能力包；每完成一套就执行批量转盘模拟，检查同序列、相邻序列和跨两级序列，再由人工检查原著定位、克制、代价和叙事结果。发现底层缺口时回到台账，不给单个能力开隐形后门。

### 4. 交付验证

分开记录：自动测试、集成状态、玩家验收、打包、安装/运行和发布。任何一项不能冒充另一项。小模型、RAG、真实原文语料和外部服务没有证据时分别标为 `NOT_RUN`/`NOT_AVAILABLE`，不升级为完成。

## 5. 可执行的文件级落点（提案）

以下目录和接口目前尚未创建，均为待实现的责任边界；它们不是现有 API 或已完成模块。

实现时按责任拆分，避免参考项目的全局脚本和 gmzz 的大领域文件重新耦合：

```text
src/domain/          CharacterState、WorldState、能力/资源/知识/经济类型
src/simulation/      weekly-pulse、NPC/事件候选、经济与恢复输入
src/resolution/      general-check、roulette、combat、consequence
src/content/         schema、版本、校验器、首版 fixture/能力/事件卡/商品包
src/knowledge/       source-register、RAG receipt、公开知识投影
src/persistence/     Main IPC、SQLite transaction、migration、receipt
src/renderer/        Title、Creation、WeeklyShell、调查/战斗/结算组件
src/shared/          IPC envelope、PublicState、错误码、版本常量
tests/               纯规则、schema、重放、投影、IPC、渲染布局
```

建议的依赖方向只有：`renderer → shared`，`persistence → domain/resolution/simulation`，`content → domain`；`domain/resolution/simulation` 不依赖 Electron、React 或数据库。RAG/模型服务只能调用 `knowledge` 的受控接口，不能直接调用 `commitTurn`。

### 5.1 底层接口最小切口

第一片代码不从页面开始，而是先让下面四个入口在纯函数/SQLite 测试中可调用：

| 入口 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| `resolveGeneralCheck` | 能力、难度、整数修正、行动级随机流 | 骰面、四档解决质量、有序 `ConsequenceItem[]` | 不决定题材文案，不自动把失败变成伤害 |
| `buildCombatRound` | 双方实时面板、可触及项目、内容版本 | 次数盘、能力盘、回合快照、随机流游标 | 不由 UI 配牌，不在胜负盘判生死 |
| `resolveCombatRound` | 已完成的双方能力盘命中与基础战势 | 胜负盘结果、因果结算输入、生存分支 | 不重复生成已提交的随机数 |
| `commitTurn` | 已验证的 resolution、状态版本、receipt | 单事务新状态、下一周摘要、回执 | 不接受 Renderer 直接写状态 |

所有入口必须是可重放的：相同状态版本、内容版本和随机流收据得到相同结果；未知情况也必须有可记录的底噪/因果来源，而不是 `Math.random()`。

### 5.2 最小纵切

真实可玩顺序固定为：标题页 → 六步捏人 → 普通人第一周 → 学习/调查之一 → 事件卡/普通判定或线索 → 末次行动 → 周结算 → 下一周。战斗先用一张调查事件卡和占位能力接通，待转盘回放测试通过后再录入真实能力。这样先验证完整玩家路径，而不是先堆一批无法进入游戏的内容。

| 片 | 必须看到的结果 | 完成门槛 |

| S3 战斗转盘 | 次数盘、能力盘、胜负盘、生存盘 | 双方盘完成后才判胜负；胜负不判生死；死亡封存 |
| S4 结算与纪事 | 周结算、摘要/完整纪事、六类终局卷宗 | 世界日志摘要不爆屏；死亡不可回档；历史封存可读 |
| S5 内容管线 | schema/lint/来源、占卜家序列9首包 | 非法内容拒绝载入；批量模拟和原著人工复核有独立记录 |

每片都必须分别记录 `AUTOMATED_TEST`、`INTEGRATION`、`PLAYER_ACCEPTANCE`、`PACKAGE`、`RELEASE`。未运行的证据保留 `NOT_RUN`，不能以“代码已写”替代。

## 7. 依赖与停止条件

- R1 合同冻结后，按常驻周仪表盘、全屏遮罩战斗和神秘学卷宗/工作台视觉建立桌面壳；批量真实事件内容和模型生成链仍等待后续内容批次，不因 UI 封板自动开始。
- 在 S0 的随机流/事务/公开投影测试通过前，不录入大量能力内容。
- 任一能力无法由统一字段表达时，先登记扩展处理器和测试，再录入该能力；不在事件配置中塞任意函数。
- RAG 小模型属于可选检索/摘要服务，不是第一条可玩纵切的硬依赖；缺失时必须有本地检索和模板降级。
- 参考项目和 gmzz 始终只读；任何抽取都先复制到本项目独立目录并做许可证、来源和 hash 记录。
