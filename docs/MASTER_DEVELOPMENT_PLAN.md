### 从参考项目保留的正面结构

- 紧凑捏人、常驻档案/纪事、底部行动区、中央事件卡和一局终局卷宗；
- 有限行动后自动世界脉冲；

### 明确不继承的问题

- 不采用全局脚本、任意函数事件、直接拼接 HTML 或 `Math.random()`；

- 页面变化不能作为保存成功证据，提交必须有 SQLite 事务回执并通过重启恢复测试。

## 2. 工程形态

第一版是单机 Electron 桌面应用，不是网络前后端。为了并行开发，仍把它拆为两条职责清晰的工作流：

- 前端：Electron Renderer，React + TypeScript + Vite，只消费公开投影并发送类型化意图；
- 后端：Electron Main、preload、领域规则、判定/模拟、内容校验和 SQLite 权威持久化；
- 主任务：共享合同、根配置、轮次合同、集成测试、接线、Git 和用户审查。
- 设计 Grill：在独立 worktree 中逐题确认未决设计，先更新台账/主题 MD，再交给主任务合入；不写产品代码。

详细依赖和信任边界见 `ARCHITECTURE_CONTRACT.md`。

## 3. 每轮固定状态机

1. 设计 Grill 任务把本轮依赖的新决定写入台账/主题 MD；主任务审查合入后冻结 `ROUND_ID`、合同版本、共享类型、写集、验收场景和停止条件。
2. 前端/后端从同一已知基线在独立分支/worktree 并行实现；任何越界改动先报给主任务。
3. 两边分别提交原子变更和证据，状态到 `READY_FOR_INTEGRATION` 后停止。
4. 主任务重新读取源码与提交头，先检查合同冲突，再按轮次声明的顺序接线；不直接相信任务摘要。
5. 主任务运行类型、规则、schema、契约、集成、构建和桌面 smoke 门禁；失败则退回对应任务，不升级状态。
6. 主任务向用户展示本轮实际界面/流程、已知缺口和证据；用户明确通过后才写 `PLAYER_ACCEPTANCE=PASSED`。
7. 只有上一轮接线和用户审查关闭后，主任务才冻结下一轮合同。

`READY_FOR_INTEGRATION ≠ INTEGRATED ≠ PLAYER_ACCEPTED ≠ PACKAGED ≠ RELEASED`。

## 4. 分轮路线

### R0 — 开源与治理基线

主任务独占：本地 Git、MIT 代码许可证、NOTICE、README/贡献/安全说明、架构合同、写集、轮次账本和任务注册。公共 GitHub 远端与发布在实际建立前保持 `NOT_CONFIGURED/NOT_PUBLISHED`。

用户审查：开源边界、主计划、前后端权限和第一轮范围。

### R1 — 桌面壳与权威状态边界

`STATUS=INTEGRATED_AWAITING_PLAYER_ACCEPTANCE / MASTER_GATE_SHA=14d17c60eb910137a270c645993d374ab74f5231`

- 前端：标题页、无存档态、周仪表盘空壳、中央叠层和 mock bridge；
- 后端：Main/preload 启动、SQLite 元数据/迁移、幂等回执、最小公开投影；
- 接线：真实 preload/IPC 替换 mock，验证启动、创建 fixture、重启恢复、重复提交不重复生效；
- 用户审查：1280×720 实机壳、信息层级和交互节奏。

### R2 — 紧凑捏人与普通人第一周

- 前端：六步紧凑捏人、派生摘要、四行动按钮与行动预览；
- 后端：捏人领域校验、派生 fixture、行动次数、保存/恢复和末次行动自动周脉冲；
- 接线：标题 → 捏人 → 第一周 → 一次行动 → 周结算 → 下一周；
- 用户审查：捏人是否足够简洁、周面板是否像游戏而非表单。

### R3 — 普通判定与事件卡纵切

- 前端：阻塞卡、最小待处理列表、精确难度/概率、后果和纪事；
- 后端：确定性随机流、d100 四档、有序因果后果、事件候选/冷却/保底、一条三阶段 fixture；
- 接线：学习或调查触发普通判定/事件，行动成本不可通过返回撤销；
- 用户审查：事件卡密度、信息公开、公平性和戏剧性。

### R4 — 经济、黑市与季度拍卖

- 前端：现金/产业概览、黑市浏览/挂牌/买卖、季度拍卖界面；
- 后端：非固定工作收入、最小产业规模、交易事务、市场事件和季度触发 fixture；
- 接线：工作收益进入权威存档，黑市/拍卖影响资源并能生成事件卡；
- 用户审查：金钱是否有用、市场是否简洁且符合世界氛围。

具体手续费、挂牌时长、NPC竞价和生活/债务细数在本轮合同冻结前 Grill；不提前臆造。

### R5 — 战斗转盘与生存/终局

- 前端：次数盘、双方实时能力盘、双方完成后的胜负盘、因果/生存结果和终局卷宗；
- 后端：回合快照、来源权重、掌握度、基础战势、胜负只判胜负、因果生存、死亡封存；
- 接线：调查事件 → 占位战斗 → 胜负 → 因果/生存 → 继续或死亡终局；
- 用户审查：转盘概率分布、位格压制、战斗可读性和克苏鲁式结果。

只用占位能力验证底层；不在此轮批量设计三条途径能力。

### R6 — 非凡成长与首个真实内容包

进入本轮前必须 Grill：第一份魔药的获得/选择、扮演与消化、晋升、0掌握度可用性，以及首个真实序列能力包的逐项效果。完成后再实现一条途径序列9的真实内容、内容校验和构建期 RAG 文本变体流程。

用户审查：原著贴合、成长节奏、能力效果和知识/剧透边界。

### R7 — 内容扩充、平衡与交付准备

分包完成三条途径序列9—7、90张独立事件与9条三阶段链，运行批量模拟和人工原著审查。最后才进入打包、安装、干净环境验证和公开发布评估；任何未运行项保持 `NOT_RUN`。

## 5. 轮次完成定义

每轮必须同时满足：

- 前端和后端各有锁定提交头、写集和测试回执；
- 主任务完成真实接线，不保留只在 mock 中成立的主路径；
- 自动门禁终态明确，失败/未运行如实记录；
- `PROJECT_STATE_LEDGER.md`、`ROUND_LEDGER.md` 和两个工作流状态一致；
- 用户看过本轮实际体验并明确通过，或本轮保持 `AWAITING_PLAYER_REVIEW`；
- 不把下一轮的设计空缺静默塞进当前实现。

## 6. 当前可开工与仍待 Grill 的边界

R0—R3 的技术结构、fixture 和占位纵切已经足够明确；R4 可先搭市场事务骨架但具体经济数值需在该轮前确认；R5 可用占位能力实现通用转盘；R6 及真实能力/原著事件内容必须继续由用户逐项把控。旧文档中“约27道基础问题”是后续内容与数值问题盘点，不再解释为阻塞桌面壳、存档、随机流或事件 schema。
