# 重构与开发流程

2026-10-09本轮执行目标已收敛，见[第一份可玩版方案](PLAYABLE_SLICE_PLAN.md)。用户要求设计汇总后整体确认再制作。确认后的顺序是普通周→首案和普通追击→基础Electron/SQLite存档→端到端修复交付；文中后续里程碑仍是长期路线，不作为本次验收的额外范围。以下9月7日设计派发计划已经走过，22条候选均已收齐，不再重复派发。浏览器内存阶段只是中间审查，不满足此次基础存档交付。

## 目标

本轮不是继续堆文档治理，而是以现有设计为依据重新构建可玩的游戏。开发以纵向切片推进：每个阶段都要让玩家完成一段真实流程、看到状态变化并能判断是否有趣。

技术路线已经确定为 React + TypeScript + Vite 浏览器审查面，以及后续 Electron + SQLite 桌面版本；用户明确不采用Godot，也不建立混合运行时。当前设计阶段不会因外部Skill的引擎示例改变技术栈。

## awesome skills 路由

每个任务先用 `.agents/skills/router/SKILL.md` 判断类型，再只加载必要 Skill。

| 工作 | 主要 Skill | 用途 |
|---|---|---|
| 整体 RPG 系统、成长、经济、战斗 | `rpg` | 数据模型、派生属性、内容与系统连接 |
| 周仪表盘、角色创建、弹层、战斗界面 | `game-ui-ux` | 屏幕栈、焦点、响应式、反馈和可访问性 |
| 事件卡、NPC 对话与分支 | `dialogue-systems` | 节点图、条件、稳定文本 ID、可回放状态 |
| SQLite 存档与迁移 | `save-systems` | 纯数据、版本、迁移、原子写入和备份 |
| 原著关键人物、轻量具名角色与组织议程 | `game-ai` | FSM/Utility 分层、可调试决策，不用模型裁决规则 |
| 新机制最小验证 | `prototype-fast` | 单问题原型、明确成功/失败标准、验证后重写或丢弃 |

需要音频、素材、性能、手感或发布时再加载对应 Skill，不提前把所有 Skill 引入任务。

6. 准备实现：按普通人的一周 → 事件与世界反馈 → 占卜家9非凡成长/战斗 → 桌面存档 → 扩展途径的可玩切片安排模型。此阶段才创建产品实现任务。

设计检查使用代表性算例和规则复核；实现时对随机、伤势、存档与隐藏信息等规则做针对性测试，界面修改同时检查可见反馈。

并行途径稿保存在各任务的 `docs/pathways/<pathway>.md`，每稿含基础、量化、机制、事件四部分与一小段当前状态；主对话汇总后四个公共入口链接对应正文，不保留两份互相竞争的完整规则。压缩后只读取当前进度与本任务关联的设计。

## 实现原则

- 现有代码不是必须全部保留，也不是必须全部删除；按真实价值逐模块保留或重写。
- 优先保留已经有测试的确定性随机、日历、普通判定、事件选择与公开状态边界。
- 旧治理测试、架构哈希、轮次状态和回执同步不进入新实现。
- 不先建“大而全”的抽象层。每个抽象必须服务当前或下一个明确切片。
- 正式内容数据和通用规则分离；暂缺内容使用带 `fixture` 标记的独立数据包。
- 浏览器阶段与桌面阶段共用领域规则和公开合同，不写两套玩法。

目标模块关系、内部/公开状态拆分和执行链见 [游戏运行时与重构架构](TECHNICAL_ARCHITECTURE.md)；途径纵切的玩家状态流与内容包结构见 [途径玩法与内容架构](PATHWAY_GAMEPLAY_ARCHITECTURE.md)。

## 里程碑 1：普通人的一周

目标：从新游戏到一周结算形成可重复游玩的完整闭环。

必须包含：

- 六步角色创建与实时属性预览；
- 出身决定职业可达性；
- 四个行动直接提交；
- 动态行动次数、状态和资源消耗；
- 工作、学习、调查、休养各一条真实结算；
- 四个行动都能进入统一事件候选流程，并在实际契合时形成扮演证据；
- 普通 d100 四档结果；
- 行动后轻反馈、底部回执和完整周脉冲；
- 至少一张真正阻塞且可选择的事件卡；
- 日期、金钱、健康、精神、灵性、知识与线索的可见变化；
- 同一 seed 可重放同一结果；
- 浏览器刷新会重置，并明确标示为开发试玩。

完成标准：真实浏览器中连续完成角色创建和至少两周流程，没有阻塞错误；玩家能够解释每次关键数值变化来自哪里，并能看出日常行动、事件卡与世界回应属于同一循环。

## 里程碑 2：事件卡与世界模拟纵切

目标：先验证主要内容机制与分支世界能够可靠运行，再把大量途径内容接上去。

必须包含：

- `EventTemplate → NarrativeVariant → EventInstance` 三层数据；
- 规则模板固定事实、条件、选项和后果，叙事变体不能改变推进身份；
- 工作、学习、调查、休养与周脉冲共用候选、冷却、重复衰减和一次一张阻塞卡；
- 一名手工设计的原著关键人物、一名轻量具名角色和一个主要组织的最小状态；
- 人物关系阶段、近期原因与组织定性注意；
- 人物死亡/失效或关键条件改变后，旧卡被取消、替代或进入分支的连续性重验；
- 普通人日常池与成为非凡者后约70%非凡相关事件的可统计标签；
- 固定文本离线运行；构建期 RAG/小模型叙事变体通过审核后缓存，运行时即时文本可回退并随实例保存。

完成标准：同一 seed 可重放至少两周事件与世界变化；改变关键人物状态后，后续事件不会引用失效角色；关闭模型不改变任何选项、规则、结果或存档。

## 里程碑 3：占卜家序列 9 纵切

目标：验证普通人生存循环如何接入非凡成长，而不是一次性铺开 22 条途径。

必须包含：

- 合法来源的魔药线索、材料与配方内容；
- 轻量调配流程与失败风险；
- 晋升到占卜家序列 9；
- 掌握度 0—500 与至少一个节点反馈；
- 一项日常能力影响调查或事件；
- 一场完整的战术姿态 → 次数盘 → 双方能力/目标盘 → 回合胜负盘 → 败者伤势/死亡/机制盘，并能带状态进入下一回合；
- 污染、精神、灵性与死亡封存边界；
- 固定审核文本全程可运行，RAG 关闭不影响玩法。

完成标准：玩家能从普通人走到第一次非凡使用与至少两回合战斗结算，且所有姿态、次数、能力、目标、伤势与状态变化可解释、可重放、可测试。

## 里程碑 4：内容生产底座

目标：让事件、能力、材料、封印物和 NPC 内容可以稳定扩充。

- 建立版本化 schema 和内容校验；
- 建立稳定 ID、来源状态和引用完整性检查；
- 建立事件链、冷却、重复衰减和确定性抽取；
- 建立共享事件模板、逐途径成长弧参数包及参与者连续性校验；
- 建立能力处理器注册表，特殊机制必须有测试；
- 建立合法内容库和可选 RAG 检索/回退；
- 制作第一批正式事件与第一件完整封印物。

## 里程碑 5：扩展到 22 条途径

每条途径遵循同一生产顺序：

1. 原著核验与序列骨架；
2. 基础量化、配速、次数盘和能力盘；
3. 战斗能力与日常效果；
4. 特殊机制；
5. 材料、配方、调配和仪式；
6. 自动测试、模拟和真实游玩；
7. 平衡修正后进入正式内容包。

占卜家完成后，用同一内容管线推进观众和猎人，再分批扩展其余 19 条。候选数值不因写入数据文件而自动变成正式平衡。

每条途径还必须拥有“接触—早期成长—势力/组织冲突—终局”四阶段事件弧。势力阶段不强制入会，任何途径都必须保留无需正式组织身份的成长路线。共享117个事件定义只是普通人和低序列的第一批公共底座，不是数量上限。后续先为序列9—0分别制作符合位格的问题模板，再为同序列的每条途径制作独立内容变体；模板可以共用结构，但切入、能力路线、关键选择、扮演证据和后果不能全途径共用。配速只按游戏周、晋升成熟度和实际试玩调整，不再按现实小时压缩。

## 里程碑 6：桌面存档与完整周目

- 接回 Electron Main/SQLite，不改变浏览器已验证的领域规则；
- 支持多个周目槽位，每槽一个滚动自动存档和一个系统恢复备份；
- 行动、事件、交易、晋升和每个完整战斗回合在提交边界自动保存；
- 不提供事件前/战斗前手动回滚，死亡槽位只读封存；
- 验证迁移、崩溃恢复、重启一致性、多个非死亡结局与序列0最高层级终局；
- 完成桌面 smoke、打包和干净机器验证后，才讨论发行。

## 每个切片的工作循环

1. 明确玩家目标、输入输出、失败条件和可见反馈。
2. 阅读相关设计、源码与测试，保留无关改动。
3. 写或更新行为测试，再实现最短端到端路径。
4. 运行相关测试、完整类型检查和生产构建。
5. 有可用图形环境时检查布局、焦点、键盘操作与控制台。
6. 审阅差异与验证证据；重大玩法分歧先讨论。

## 原型策略

`prototype-fast` 只用于回答一个具体未知问题，例如“多回合转盘的一个完整回合是否能在 60 秒内被理解”。原型放在独立目录，开始前标记 `THROWAWAY` 或 `KEEP`：

- `THROWAWAY`：只验证体验，不接入正式数据与存档；
- `KEEP`：验证通过后仍需按正式类型、测试、可访问性和存档边界重写，不能把临时代码原样升级为生产代码。

## 验证层级

- 单元测试：规则与边界；
- 集成测试：公开意图到状态回执；
- 真实浏览器：实际玩法、布局、焦点与反馈；
- Electron/SQLite：持久化、重启恢复与桌面安全；
- 打包与干净机器：发行前单独验证。

后一层不能由前一层替代，但也不需要用历史状态码和多份账本重复记录。
